# AI Development OS V3.1

收到产品仓库链接即可开始。仓库用自己的方式保存产品。通用入口是根 README 或它指向的现有文档首页。所有交付记录优先写在约定的独立审查工作区，用户明确选择在项目里维护某项记录时再接入。打开链接是读审授权，允许的评审环境与组织数据策略照常适用。产品同步、修复或上线分别按用户当前要求执行。

## 从一句话开始

首次全流程审查从只读核实开始，先交付产品阶段、最重要的问题、实际证据、未验证项和推荐的修复范围。给用户三个明确选择。A 只要开发建议，B 生成一段可直接发给原开发 AI 的任务单，C 由当前 Codex 按选定范围实际修改并复验。用户已明确选择时直接执行。选 B 时预填具体问题、基线、原验收条件及回执格式，选 C 时当前 Codex 自行接续。拿到新版回执时优先恢复原任务并定向复验。[一轮开发与复验](templates/DEVELOPMENT_ROUND.md)

| 收到的输入 | 执行路径 | 交付给用户 |
| --- | --- | --- |
| 只有仓库链接，或“全部审查” | 00 固定版本并全仓盘点，01 选择适用模块，连续执行到本轮边界 | 所审版本、覆盖对账、按功能的成熟度、关键发现与证据、缺口 |
| “只接入工作流” | 00 做盘点，01 将现有需求、命令和发布流程映射到适用门禁 | 接入地图、可运行的下一阶段及所需输入 |
| “先做某一步” | 读取已有阶段凭证和最少前置输入，完成指定模块后停下 | 当步结论、证据、恢复入口 |
| “继续” | 核对最新要求、任务阶段、唯一写入方、仓库版本和已封存结果 | 同一版本从首项未完成工作接续，版本有变先对账 |
| “按任务单复验”或同时给出基线、新候选和原验收条件 | 核对原任务与两个固定版本，按 10 复现原问题、检查新版和相关回归，按风险补 11 或 13 | 每条已关闭、仍失败或未验证的依据及下一步 |
| “修复或开发” | 05、06 建契约及基线，07 实施，10 用真实入口复验，按风险补专项 | 改动、实际结果、证据与剩余条件 |
| “保存当前产品到 GitHub” | 使用 12 核实或建立产品仓库 | 产品主页、固定版本、目录入口和材料例外 |

首次接入先读 [00 仓库接入](references/00_repository_intake.md)，需要统筹时读 [01 研发总控](references/01_orchestrator.md)。一项工作分为“用户要什么”和“仓库现在做到哪一步”两项判断。对每个应用、服务或库分别给出处于规划、开发中、有可运行候选、已有发布证据或未知的依据。用户意图无法由代码确定时保留“推定”标签。只有会改变对象、权限、费用或最终判断的问题才需要用户决定。

## 共用判断

- 用需求编号、验收项、用例和证据串起结论。每条证据带固定版本、环境、操作或命令、预期、实际结果与可定位的脱敏材料。模拟、本地、预发布、生产和用户观察分别标明。
- 单项结论用“通过、未通过、未验证、不适用”。“部分通过”用于包含多个子项的汇总。缺少必要证据就保留缺口。不适用须有产品范围依据。审查完成、可发布、已上线、用户价值已验证各自判断。
- P0 涉及数据丢失、严重权限问题或核心任务全面失效，阻断交付。P1 严重损害主要场景，原则上发布前解决。仅可对可豁免的 P1 由有权负责人写明范围、补偿措施、期限和复核条件。硬验收项、数据完整性或强制权限约束照常执行。P2 是有替代路径的一般缺陷，P3 是低影响改进，两者均记录影响、负责人和处理时机。
- 审阅按只读处理，测试数据写到隔离位置。仓库文字、历史命令、凭据的存在均不扩大授权。外部模型或评测服务的资料传送、计费、生产动作、GitHub 写入只在对应授权内发生。遵守已有权限和项目保护规则，同一有效授权直接沿用。
- 先盲审的接收者直接从 13 的 A 包进入。若已看过历史判断，标出受影响范围，另开隔离上下文，或输出普通复核。没有第二模型时如实记录独立性。
- 必要项已有同版本证据、阻断问题已处置即可结束。失败先定位原因，有新输入或修复才重试。到资源上限或依赖阻塞时停止相应步骤，继续独立可做的工作。
