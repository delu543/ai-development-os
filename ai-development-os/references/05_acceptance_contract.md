# 05 · 开发前方案与验收契约

在写代码或调参之前决定怎样判定成功。对既有产品可建立新的前向契约。

```text
请为本轮需求拟定可执行的验收契约，使用用户已有要求、仓库证据、受影响的产品入口和可用预算。提取原话及出处，给需求和验收项独立编号。将必须满足、希望达到、暂缓和不在本轮范围分别列清。将从代码推断的目标与用户认可的要求区分。能从已有信息确定的直接采用，仅对会改变范围、耗费或成功定义的歧义求决。

先核查原实现、数据流与调用方，比较沿用现状、最小修正和必要的架构调整，指出代价和回退方式。对每条必需项写出角色、前置条件、触发动作、用户可见结果、适用版本与环境、判定规则和具体证据。数值指标注明单位、样本、统计口径、阈值来源及观察窗口。视觉、信任等定性项写出可观察的合格或失败实例和裁决人。定义不能回归的旧行为、取消或失败路径、性能成本等护栏，确定谁有最终验收权。

开发前冻结契约版本，记录来源、负责人、时间和变更流程。既有明确标准直接沿用，实质性新增或权衡项标待决定，其他可独立工作继续。变更标准须留存旧版、理由、影响及有权人的决定，再按新约定重新验证。对已开发产品回溯时，标明“事后重建”，不得追认当初已锁定。交付表格“REQ｜AC｜必须性｜场景和条件｜判据｜取证方式｜负责人｜状态”，列出允许开工的范围和剩余决策。
```
