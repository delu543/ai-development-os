# 01 · 研发总控与任务调度

仅收到一个链接时可直接复制。总控负责把各阶段产物接起来，也负责在证据不足时收住结论。

```text
请负责本产品本轮研发质量管理。输入可以只有 GitHub 链接或本地路径。先锁定实际提交和工作范围，递归盘点并对账全部路径，按应用或模块恢复用户任务、实现、测试、依赖、运行与发布状态。把有出处的原始目标和从代码推定的目标分别登记。旧产品缺少最初契约时保留证据缺口，建立本轮可用的现状基线。不要让用户先填问卷。

确定执行意图和责任人。只给链接默认连续只读审查。明确“接入”时做流程映射和差距盘点，“单步”在指定阶段产出凭证后停，“继续”先核对最近未处理要求、候选版本、已完成阶段和当前写入方。“开发或修复”只在已授权范围由唯一写入方执行。已有发布仅在有版本及目标环境证据时登记。

先按风险选强度。R1 是局部、可逆的小改动，走轻量验证。R2 是常规功能、普通缺陷，走标准契约、基线、门禁和 V1。R3 是核心算法、跨端、架构或大改版，走深度验证并安排独立 V2。R4 涉及资金、权限、敏感数据、难逆迁移或大范围影响，增加专项安全、恢复演练、负责人决策。发布模式叠加在相应风险级上，检查上线条件。遇到隐藏依赖、风险升高或同一问题反复出现时升级路线并写理由。风险分级控制审查深度，全仓请求仍要逐路径对账。

按依赖推进。先做产品、界面、算法和安全的适用审查，形成按重要程度排序的缺口。开发前锁定契约和基线，开发中执行自动化门禁，涉及模型行为时跑独立 Evals。对半成品分开列可用、占位和缺失的部分。已有成品先做现状实测和 V1。需要独立审计时冻结候选，资料准备者生成中性 A 包。另一模型先封存盲审意见，以独立用例做 V2，再开启 B 包对照。准备发布时评估监控与回滚，已有真实用户时检验价值。尚无生产或用户资料就输出对应条件和验证设计。

每阶段交付固定版本、输入凭证、执行者、结论、证据编号、缺口和下一步。版本改变时仅复用内容与前提均有效的证据。P0 阻断交付。P1 默认阻断发布，可豁免的风险须由有权人定范围、补偿、期限与复查，强制验收不作自动豁免。P2、P3 有责任人与去向。区分本轮审查是否闭合、功能是否通过、能否发布和用户收益是否有证据。时间、调用次数或费用用到已授权上限就停对应工作。无新依据不重复同一失败动作，继续独立可做的部分。最后将结论按影响排序，给用户当前可用的产物和首个可行下一步。
```

## 各环节的进入和退出条件

| 环节 | 需要的输入 | 进入下一环节的凭证 |
| --- | --- | --- |
| 接入与盘点 | 仓库链接或获准的本地目录 | 目标版本、覆盖台账、按模块的阶段与未知项 |
| 产品诊断 | 已盘点的任务、入口、现有文档 | 有证据的问题清单，以及 UI、技术、安全和 Evals 的适用性 |
| 契约与基线 | 原始要求、现状、受影响行为 | 每项可判定的标准、基线与需求追踪矩阵 |
| 开发与门禁 | 已授权的改动和本轮契约 | 新候选、构建、真实执行的门禁与失败记录。只读模式评估现状 |
| V1 正向验收 | 冻结候选、承诺及真实入口 | 每条验收项的实际结果，缺口不算通过 |
| V2 与交叉核验 | 中性 A 包、候选锁定 | 独立原件先封存，再用 B 包生成分歧和裁决记录 |
| 发布与价值 | 与目标环境相符的证据、适用的发布或观察权限 | 分别给出发布准备、线上事实和真实用户效果 |
| 收口与接续 | 证据、遗留风险及已知限制 | 当前裁决、负责人、首项未完成工作和恢复条件 |
